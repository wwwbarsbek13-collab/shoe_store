## 1. SQL-инъекции

SQL-инъекция возникает, когда пользовательский ввод непосредственно включают в текст SQL. Исследование выполнено **на RAM-копии** исходной базы, без воздействия на рабочие таблицы.

Учебный пример уязвимого кода:

```python
cursor.execute(f"SELECT user_id, login FROM users WHERE login = '{login}'")
```

При вводе `' OR '1'='1` условие в SQL становится истинным для всех строк. Демонстрация показала 3 записи вместо одной. Такой код существует только в изолированном `src/security_demo.py` как намеренно небезопасный образец.

Исправление:

```python
cursor.execute("SELECT user_id, login FROM users WHERE login = ?", (login,))
```

При том же вводе результат **0 строк**. Символы `?` в SQLite передают значения отдельно и не дают превратить их в часть SQL-команды.

### Три примера исправления запросов с пользовательским вводом

**1. Поиск пользователя по логину**

```python
# ДО (небезопасный пример)
conn.execute(f"SELECT user_id FROM users WHERE login = '{login}'")
# ПОСЛЕ (src/security_demo.py)
conn.execute('SELECT user_id, login FROM users WHERE login = ?', (login,))
```

**2. Поиск модели обуви**

```python
# ДО (небезопасный пример)
conn.execute(f"SELECT product_id FROM products WHERE product_name LIKE '%{term}%'")
# ПОСЛЕ (src/security_demo.py)
conn.execute('SELECT product_id, product_name, price FROM products WHERE product_name LIKE ?', (f'%{term}%',))
```

**3. Выбор заказов конкретного клиента**

python
# ДО (небезопасный пример)
conn.execute(f'SELECT order_id FROM orders WHERE user_id = {user_id}')
# ПОСЛЕ (src/security_demo.py)
conn.execute('SELECT order_id, order_date FROM orders WHERE user_id = ? ORDER BY order_id', (user_id,))

### Фактическая проверка

| Проверка | Итог |
|---|---:|
| Обычный логин `admin` (учебная копия) | 1 строка |
| SQL-инъекция в уязвимом поиске | 3 строки |
| SQL-инъекция в параметризованном поиске | 0 строк |
| SQL-инъекция при поиске товара | 0 строк |

## 2. Хранение паролей

В таблицу `users` добавлено поле `password_hash TEXT`. В `src/auth_secure.py` реализованы:

- `hash_password(password)` - возвращает `hashlib.sha256(password.encode('utf-8')).hexdigest()`;
- `register_user(conn, login, password)` - проверяет уникальность и сохраняет только хэш, пользователь получает минимальные права `reader`;
- `check_password(conn, login, password)` - через `hmac.compare_digest` проверяет совпадение хэша и добавляет запись в журнал входов.


## 3. Разграничение прав и минимальные привилегии

`src/admin.py` хранит словарь прав `PERMISSIONS`:

| Роль | Доступ |
|---|---|
| `admin_db` | SELECT, INSERT, UPDATE, DELETE, CREATE, DROP |
| `developer` | SELECT, INSERT, UPDATE |
| `reader` | только SELECT |

Функция `check_permission()` запрещает любое действие вне списка. Например, у `reader` запрос `DELETE` возвращает False, а у `admin_db` - True (на тестовых учетных записях). **В SQLite это контроль приложения, не ограничение прямого доступа к файлу**.

## 4. Аудит действий и попыток входа

С практики №11 сохранена таблица `audit_log`, которая фиксирует изменения цены товара и удаления заказов. В практике №13 добавлена таблица:

`login_audit(id PK, login, status ['успех'/'отказ'], login_time)`.

Всякая попытка аутентификации вызывает INSERT в `login_audit`. На RAM-копии подтверждены записи как `успех`, так и `отказ` при корректном и ошибочном пароле. В рабочей базе сохранены учебные записи отказа для несуществующего логина и инъекционной строки без каких-либо изменений чужих учетных данных.

**Рекомендации для реальной системы:** логировать дату и категорию события, ограничивать количество попыток входа, не записывать пароль или его хэш в журнал, архивировать логи и закрывать доступ к ним обычным пользователям.

## 5. Защита самого файла базы данных

SQLite - файловая БД. Нужно ограничить чтение, запись и копирование файла:

- Linux: владелец базы и `chmod 600 db/shoe_store.sqlite`, защищенный каталог и права на бэкапы.
- Windows: ACL-права на папку и базу, доступ только приложению и администратору.
- Использовать резервные копии с ограниченным доступом, не включать реальные секреты в публичные ZIP и Git-репозитории.
- Не запускать приложение постоянно с административными правами.
- Перед восстановлением останавливать все процессы, открывающие базу.
